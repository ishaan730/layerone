The short answer

Not all components are equal: a badge takes days, a data table can take months. Sort components into four levels: elements (show something), controls (one clear interaction), composites (several parts that coordinate) and systems (data, logic and performance). For planning, score each one 0–3 on eight questions (options, states, interaction, keyboard and screen reader, data, screen sizes, composition, platforms) and add them up. Then match the process (people, research, testing, beta length) to the level, and plan by points rather than by component count.

  • 0–6 points is level 1, 7–12 level 2, 13–18 level 3, 19–24 level 4.
  • A date picker scores like a composite, not a select menu: dates are data, and the calendar grid has demanding keyboard behaviour.
  • Each extra platform adds roughly the same effort again.

Why "ten components this quarter" misleads

Plans that count components treat a divider and a data table as the same unit of work. They're not, and the result is predictable: the quarter's plan looks on track until the one complex component swallows two months. Leadership loses confidence, and the team gets blamed for a planning model that was wrong from the start.

Complexity also matters for process. Running a heavyweight process for a badge wastes everyone's time; running a lightweight one for a data table guarantees bugs in production.

Four levels of complexity

These loosely echo Brad Frost's idea of building from small parts to large ones, but they're organised by how hard something is to get right, not by how big it is.

Level 3 is where accessibility gets genuinely hard: a menu has a trigger and a list, tabs have a tab list and panels, a dialog manages focus for everything inside it, and people expect established keyboard patterns. Level 4 components are small applications in their own right and often take longer than everything else in the library combined.

Scoring complexity: eight questions

Levels are a good first guess. For planning, rate each component 0–3 on eight questions and add them up. You don't need precision; the point is to have the conversation as a team before committing to dates.

Match the process to the level

For level 3 and 4 components, start with a kick-off workshop with every team that will use the component: walk through every existing version, agree must-haves and out-of-scope items, and name the pilot team. People support what they helped shape.

Plan by points, not by count

Instead of "ten components this quarter", plan with the totals: "about 90 points this quarter". A badge is 2 points; a data table is 22. It sounds a little nerdy, but it makes plans honest overnight, and it gives leadership a much better picture of progress than a count of finished components.

The same scores help with request prioritisation: complexity is the "effort" that divides a request's value score.

Choose the simplest component that works

Complexity is also a design decision for product teams. Every time a designer picks a component, they pick a level of complexity for users and for the engineers who'll build the screen. The simplest component that does the job is almost always right.

The short version

  • Four levels: elements, controls, composites, systems.
  • Score components 0–3 on eight questions to place them and estimate effort.
  • Match people, research, testing and beta length to the level.
  • Plan by points, not by number of components.
  • For product teams: choose the simplest component that does the job.

Frequently asked questions

How long does it take to build a design system component?

From days for a simple element to one to three months or more for a data table, on one platform. Score the component to estimate it.

Why are date pickers so hard?

Because they combine data (locales, time zones, ranges, disabled days) with a calendar grid that needs complex keyboard and screen reader behaviour.

Should the whole team score components together?

Yes, briefly. The value is in the conversation: designers, engineers and accessibility specialists notice different sources of complexity.

How do we re-score as we learn more?

Re-score yearly, or when a component's scope changes. Scores also help explain to leadership why one component took a quarter.
