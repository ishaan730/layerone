The short answer

Build contrast into a design system once, at the token level, and every product inherits it. Use the WCAG 2.2 minimums: 4.5:1 for body text, 3:1 for large text and for meaningful non-text elements like input borders, icons and focus rings. Check pairs, not colours (a colour is only accessible against what it sits on), in every theme. With a palette built on a shared lightness curve, simple rules emerge: in ours, any two steps six apart pass for body text, with one exception at the very light end.

  • Low-contrast text is the most common accessibility failure on the web.
  • Publish the approved pairs and test them automatically on every token change.
  • Give the accessibility owner a real veto over token value changes.

Why contrast belongs in the design system

WebAIM's 2025 scan of the world's top million home pages found low-contrast text on 79.1% of them. Measured It's the most common accessibility failure on the web, and almost always the result of colours chosen one screen at a time.

A design system changes the economics. Decide the text and background pairs once, as tokens, check them once, and every component and product built on them inherits the result. Fix a failing pair in the system and the fix reaches every screen in a release. That's why contrast is the cheapest place in the whole product to get accessibility right.

The WCAG ratios that matter

Watch out

"Exempt" isn't the same as "fine". Disabled text that nobody can read still confuses people. Keep disabled states legible, and explain nearby why an action isn't available.

Check pairs, not colours

A colour has no contrast on its own. neutral.600 is 4.57:1 on white but only 4.25:1 on neutral.50, our light canvas: it passes on one background and fails on the other. So the unit you check, document and test is the pair: a foreground token on a background token, in a specific theme.

That's another reason for semantic tokens. When colours are named by job (text.secondary on bg.canvas), the pairs that matter are finite and nameable, and you can check every one in every theme:

From a matrix like this you can write pairing rules anyone can apply without a checker:

  1. Body text: six steps apart

    Steps six or more apart pass 4.5:1, except next to the lightest step: on 50, text needs 700 or darker.

  2. Large text and borders: five steps apart

    Steps five or more apart always pass 3:1, which covers large headings, input borders, icons and focus rings.

  3. Same rule, every hue

    Because every ramp shares the lightness curve, step 700 is between 5.8:1 and 7.1:1 on white in every colour family we built. Brand, blue, red and green follow the same rule.

How to build contrast into the system

  • Pick text tokens that pass on every background they're allowed on, in every theme.
  • Publish the approved pairs on the token documentation page, with their ratios.
  • Test automatically: a script that computes every documented pair and fails the build if one drops below its minimum.
  • Check states: hover, pressed, focus and selected colours are pairs too.
  • Lint for raw colours in product code, so nobody bypasses the checked tokens.
  • Give accessibility a veto over token value changes in your decision-rights matrix.

Hundreds of hard-coded greys across several codebases, fixed screen by screen over months.

Beyond the ratio: colour and meaning

Contrast is necessary but not sufficient. WCAG also asks that colour isn't the only way information is shown (1.4.1). An error field needs an icon or message as well as a red border; a chart needs labels or patterns as well as colours. Build those patterns into components, so teams get them by default.

WCAG 2 vs APCA

APCA, the Accessible Perceptual Contrast Algorithm, is a newer method that accounts for font size, weight and whether text is light-on-dark or dark-on-light. It often gives better answers in dark mode and for thin fonts. It's a useful second opinion, but WCAG 2.2's ratios are what laws and audits measure today, so use WCAG as the gate.

The short version

  • 4.5:1 for body text; 3:1 for large text, borders, icons and focus rings.
  • Check pairs, not colours, in every theme and every state.
  • A shared lightness curve turns contrast into simple step rules.
  • Publish approved pairs, test them automatically, and lint for raw colours.
  • Don't rely on colour alone to carry meaning.

Frequently asked questions

What contrast ratio does WCAG require?

At level AA: 4.5:1 for normal text, 3:1 for large text, and 3:1 for meaningful non-text elements such as borders, icons and focus indicators.

Does the primary brand colour have to pass contrast?

Only where it's used for text or meaningful UI. Many brands use a lighter brand colour for decoration and a darker step of the same hue for text and buttons.

Should we use APCA instead of WCAG 2?

Use WCAG 2.2 as the requirement, and APCA as a second opinion, especially for dark mode and thin type.

How do we test contrast automatically?

List every allowed foreground–background pair in your token docs, compute their ratios in a script during the token build, and fail the build if any drop below their minimum.
