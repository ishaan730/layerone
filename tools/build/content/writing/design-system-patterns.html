The short answer

A design system pattern is a documented way of combining components to solve a recurring user problem, such as "how we show that there are no results" or "how we confirm a destructive action". Components are the words; patterns are the sentences. A system with good components and no patterns still produces inconsistent products, because every team combines the same parts differently. Start with the four pattern families that cause most inconsistency: forms, lists and tables, navigation and feedback (loading, empty, error and success).

  • A pattern isn't a new component. It's guidance, with the reasoning and evidence behind it.
  • Document a pattern when two or more teams have solved the same problem differently.
  • Patterns need documentation even more than components, because there's no code to copy: the guidance is the pattern.

Components are words, patterns are sentences

You can have a perfect dictionary and still write confusing sentences. Design systems have the same problem. Every team uses the system's button, text field and table, so the components are consistent. But each team combines them differently: one form shows errors at the top, another under each field, a third in a pop-up. One list paginates, another scrolls forever. The parts match and the product still feels like five products.

New word

A pattern is a proven, documented way of combining components to solve a recurring user problem. The UK government's GOV.UK Design System is the best-known public example: alongside its components it publishes patterns for asking for dates, addresses and names, each based on research with real users.

Pattern or component?

Teams often ask for a new component when what they need is a pattern, and the other way round. A quick test helps:

The four pattern families to start with

You don't need a hundred patterns. Most of the inconsistency in business software comes from four families, and writing down one answer for each removes most of the re-debating between teams.

FORMS

Where products make money

Layout, required fields, when to check for errors, where to show them, what they say, long forms and buttons. Usually the first pattern worth writing down. See form design patterns.

LISTS AND TABLES

Where people find things

Table, list or cards; pagination or "load more"; how filters, search, sorting and bulk actions work across the product.

NAVIGATION

Noticed only when it fails

The app frame, side menu or top navigation, tabs, breadcrumbs and back links, and the rules for when each is right.

FEEDBACK

Where products feel inconsistent

Loading, empty, error and success states. Each team handles them as an afterthought, so they drift the most.

Lists and tables: three choices to make once

Most business software is a collection of lists: invoices, customers, orders, users. How people find, sort and act on items decides how fast they work.

TABLE

When people compare

Many items with the same attributes, where people scan columns, sort and compare: invoices, transactions.

LIST

When people pick

Items with one or two key details, where people mostly find one and open it: messages, notifications.

CARDS

When items are visual

Where an image or preview matters more than comparison: templates, projects, products.

For filters, decide where they sit (above the list or in a side panel), whether results update instantly or after "Apply", how active filters are shown and cleared, and what the empty result says. For bulk actions, decide how people select many items and where the actions appear. Written once, these decisions stop every list in the product from working slightly differently.

Navigation: one job per component

Practitioner view

If people need to go more than three levels deep (section, page, tab) to reach something they use often, the problem is usually the structure of the product, not the navigation component. That's a conversation for product leadership, and the design system team is often the first to notice it.

Feedback: four moments, four components

Every screen has moments when things aren't normal: data is loading, there's nothing to show, something went wrong, or something just succeeded. Decide once which component carries each kind of message.

FIRST USE

Nothing yet

Explain what will appear and offer the first step: "No invoices yet. Create your first invoice to get paid faster."

NO RESULTS

Search found nothing

Say what was searched, and suggest changing or clearing the filters.

ALL DONE

Everything is cleared

A small, positive confirmation: "All invoices are paid." No action needed.

For loading, show a skeleton for short waits so the page doesn't jump, show progress on the button that was pressed for actions like saving, and always handle the case where loading fails, with a clear way to try again.

How to document a pattern

A component page can lean on live code examples. A pattern page can't: the words are the pattern. A consistent template makes patterns quick to write and easy to trust.

The evidence section matters more than it looks. Without it, a pattern is one team's preference, and the next team with a different preference will argue. With it ("we tested inline errors against a top summary with eight users; both were needed"), the conversation moves on.

When to write a pattern down

  1. Notice the second solution

    When a second team solves a problem the first team already solved, differently, that's the signal. The same "rule of two" that decides when something joins the core library applies to patterns.

  2. Collect every existing version

    Screenshot each team's solution side by side. Seeing four empty states on one board usually ends the debate about whether a pattern is needed.

  3. Agree one answer, with evidence

    Pick or design the best version with the teams involved, and test it if the stakes are high. A short working group of three to six people works well.

  4. Document it with the template

    Problem, solution, examples, variations, when not to use it, evidence, accessibility and writing.

  5. Migrate the most visible versions

    Update the screens people see most first. The rest follow as teams touch them.

The short version

  • Components are words; patterns are sentences. Consistent parts still need agreed combinations.
  • Start with forms, lists and tables, navigation, and feedback states.
  • Write a pattern down when a second team solves the same problem differently.
  • Use one template: problem, solution, examples, variations, when not to use it, evidence, accessibility and writing.
  • Evidence is what stops a pattern being re-debated.

Frequently asked questions

What is the difference between a pattern and a component in a design system?

A component is a reusable part with its own code, design, props and states, like a button or a dialog. A pattern is guidance on how to combine components to solve a recurring problem, like validating a form or showing that there are no results.

Do patterns need code?

Not necessarily. Many patterns are guidance plus examples. When a pattern is copied into many products with the same code, it can be worth turning into a component or a copyable recipe later.

Who should own patterns?

The system team owns the library of patterns, but individual patterns are often written by the product team closest to the problem, through the normal contribution process, and reviewed by the system team.

How many patterns does a design system need?

Fewer than you think. Start with the four families (forms, lists, navigation, feedback) and add patterns only when two or more teams need the same answer.
