How much design system context does an AI agent need? Avoiding context overload

Teams that give agents everything often get worse results: rules buried in 1,800-line files, a hundred tools to choose from. What fills the context window, a size budget for each layer, and a step-by-step diet for your design system context.

The short answer

Less than most teams give it, and more precisely. An agent needs a short map loaded every time (a rules file of roughly 50–150 lines: package, never-use list, token rules, where to look, how to check) and exact answers on demand (one component's props and rules, the tokens for one job, one pattern page). It does not need your whole docs site, every component's full API, or a dozen MCP servers loaded at once. Every extra line and every tool definition takes space in the context window and competes for attention, so too much context makes results less consistent, not more. Measure what's loaded, keep the always-on part small, and load the rest only when the task needs it.

  • Tool definitions count too: each connected MCP tool's name, description and schema is sent with every request.
  • If an agent ignores a rule you know is written down, first check whether it's buried.

"We gave it everything, and it got worse"

Once teams learn that agents need context (part 2), a common next step is to give them all of it: the full component docs pasted into the rules file, the token file attached to every prompt, every MCP server anyone found useful. Results often get worse.

An illustration: the 1,800-line rules file

The situation

Kestrel's payroll app has an AGENTS.md that grew to 1,800 lines: Harbor's full docs, the brand guide, API conventions, testing guides. Eleven MCP servers are configured.

The symptom

Agents follow the "never use ui-old" rule in some runs and not others. Simple tasks take noticeably longer to start. The same prompt gives different component choices from one day to the next.

The cause

The ten rules that matter are on lines 900–910, surrounded by text that's irrelevant to most tasks, and the agent is choosing between around 180 tools on every step.

What the context window actually holds

Every time an agent takes a step, the model is sent everything it needs to decide the next one. Understanding what's in that bundle explains why "more" isn't free.

New words

Token (in AI models): the unit models count text in, roughly three-quarters of an English word; not the same as a design token. Context window: the maximum number of tokens a model can consider at once. Progressive disclosure: showing a short summary first and loading detail only when it's needed.

Two separate problems come from overfilling it:

PROBLEM 1

Budget

Large windows are big, but long tasks fill them: a few big files, long lint output and tool results add up. When space runs out, agents summarise or drop earlier context, and early instructions can be lost. Larger contexts also cost more and run slower.

PROBLEM 2

Attention

Even well within the limit, models use information less reliably when it's buried among lots of other text. Research on long contexts has found that facts in the middle are used less well than facts at the start or end. Ten clear rules beat ten rules inside 1,800 lines.

Too many tools is a context problem too

Each MCP server adds its tools' definitions to every request. One design system server with four tools is small. Eleven servers, some with thirty or forty tools each, can add tens of thousands of tokens before the agent reads your prompt, and give the model far more options to choose between on every step. Engineering reports from teams running many servers consistently describe the same pattern: as tool counts grow, the cost rises and the agent picks the wrong tool more often.

Some agent products now load tool definitions on demand when many are configured, searching for the right tool instead of showing all of them up front. That helps, but it still relies on clear tool names and descriptions to find the right one.

Step by step: put your design system context on a diet

  1. Measure what's loaded

    Count the lines in every rules file that loads for a typical UI task (root AGENTS.md, nested files, CLAUDE.md, tool-specific rules), and list the MCP servers and tool counts. Many agents show context usage directly; Claude Code, for example, has a /context command.

  2. Sort every rule into three piles

    Every task (never use ui-old), some tasks (how to build a data table), reference (the full list of props). Only the first pile stays in the rules file.

  3. Move "some tasks" into on-demand places

    Pattern pages the MCP server can return, scoped rules that only apply to matching files (Cursor and Copilot both support path-scoped rules), or skills that load when the task matches their description.

  4. Move "reference" into data

    Prop lists and token values belong in the generated manifests from part 4 and part 3, fetched one item at a time.

  5. Trim the tool list

    Keep project-level MCP config to the servers the repo's work needs. Merge overlapping tools. Shorten descriptions to what the model needs to decide when to call them.

  6. Shape tool results

    Return summaries from search tools and detail from get tools. Strip fields agents don't use. Cap results (five components, eight tokens).

  7. Re-test

    Run your eval tasks (part 9) before and after. Consistency between runs is the number to watch.

Long tasks: keeping context healthy as work goes on

Context also fills up during a task. A long session that builds a whole feature opens dozens of files, runs checks many times, and accumulates output. Three habits help:

  • One task per session. Start a fresh session for each screen or ticket, so earlier, unrelated context doesn't leak in.
  • Quiet checks. Make your check command print only errors, with file, line and message. Pages of passing-test output waste space.
  • Put essentials in files, not chat. If agents compact or summarise long conversations, rules typed into chat early on may be summarised away; rules in files are reloaded.

How to tell whether context is the problem

Common mistakes

MISTAKE

Pasting docs into rules files

Docs are reference; rules files are a map. Link to the docs and let the agent fetch the part it needs.

MISTAKE

One giant MCP tool response

A get_all_components tool that returns everything fills the context in one call. Search, then get.

MISTAKE

Committing everyone's favourite servers

Project config applies to everyone. Keep it to what the repo needs; personal tools go in personal config.

MISTAKE

Trimming without testing

Removing a line can remove a rule that mattered. Rerun your eval tasks after each trim.

The short version

  • Agents need a short map every time and exact answers on demand, not everything at once.
  • Rules files and tool definitions are present on every step, so keep them small.
  • Sort rules into every-task, some-tasks and reference; only the first stays in the rules file.
  • Configure only the MCP servers a repo needs; shape tool results to be short.
  • Measure consistency across runs before and after trimming.

Frequently asked questions

How long should an AGENTS.md or CLAUDE.md file be?

As short as possible while covering what every task needs. Under about 150 lines for the whole file is a good target, with the design system section around 30–80 lines. Link to docs for everything else.

Do too many MCP servers slow down AI agents?

Yes. Every connected tool's definition is sent with each request, which uses context and adds cost, and more tools mean more chances to pick the wrong one. Configure only the servers a project needs.

Should I paste my design system docs into the prompt?

No. Give the agent a short map and a way to fetch exactly what it needs, such as a component index or an MCP tool. Pasting everything makes important rules harder to follow.

What is progressive disclosure for AI agents?

Showing the agent a brief summary first (a rules file, a component index, tool names) and loading detail only when the task needs it (one component's props, one pattern page).

Why does my agent follow a rule sometimes but not always?

Often because the rule is buried in long context, contradicted by code the agent read, or typed in chat early in a long session. Put it near the top of a short rules file and back it with a lint rule.
